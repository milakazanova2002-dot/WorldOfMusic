# WORLD OF MUSIC (WOM)

# Стандарты проекта (Project Standards)

**Версия:** 1.0
**Статус:** Утверждено

---

# 1. Общие принципы проекта

Проект разрабатывается по архитектуре **MTV (Model – Template – View)** на фреймворке **Django**.

Основные принципы разработки:

* одна модель — одна сущность предметной области;
* каждая модель отвечает только за свои данные;
* не допускается дублирование информации;
* если объект существует в реальном мире самостоятельно — он выделяется в отдельную модель;
* предпочтение отдается встроенным возможностям Django.

---

# 2. Общие правила моделей

## 2.1 Первичный ключ

Во всех моделях используется стандартное поле:

```python
id = BigAutoField
```

Явно поле `id` не объявляется.

---

## 2.2 Временные поля

Все основные модели содержат поля:

* `created_at`
* `updated_at`

Назначение:

* дата создания записи;
* дата последнего изменения.

Исключения допускаются только для справочников.

---

## 2.3 Метод `__str__`

Каждая модель должна иметь понятное строковое представление.

Примеры:

```
TeacherProfile → Иванов Иван Иванович

StudentProfile → Петрова Мария

MusicPiece → Катюша

Category → Военные

Subject → Вокал
```

---

## 2.4 Slug

Все модели, имеющие собственную страницу на сайте, используют поле `slug`.

Slug применяется:

* в URL;
* при генерации ссылок;
* для SEO.

Slug должен быть уникальным.

---

## 2.5 `get_absolute_url()`

Все модели с собственной страницей реализуют метод:

```
get_absolute_url()
```

Это позволит строить ссылки средствами Django.

---

# 3. Правила связей

## OneToOne

Используется только тогда, когда объект может существовать исключительно в единственном экземпляре.

Например:

```
User
    │
    ▼
TeacherProfile
```

---

## ForeignKey

Используется для связи

**Один → Многие**

Например:

```
TeacherProfile

↓

TeachingAssignment
```

---

## ManyToMany

Используется только тогда, когда связь действительно является отношением "многие ко многим".

Например:

```
MusicPiece

↕

Category
```

---

## related_name

Все связи обязательно получают понятный `related_name`.

Пример:

```
teacher.assignments.all()

student.assignments.all()

music_piece.performances.all()
```

---

# 4. Правила хранения файлов

Изображения:

```
ImageField
```

Используются для:

* фотографий;
* превью статей.

Документы и медиа:

```
FileField
```

Используются для:

* нот;
* минусовок;
* плюсовок;
* видео;
* текстов произведений.

---

# 5. Правила справочников

К справочникам относятся:

* Subject
* Category

Особенности:

* уникальное название;
* сортировка по алфавиту;
* редко изменяются.

---

# 6. Правила пользователей

В проекте используется собственная модель пользователя на основе:

```
AbstractUser
```

Тип пользователя определяется не полем `role`, а наличием связанных профилей.

Возможные варианты:

* обычный пользователь;
* пользователь с профилем ученика;
* пользователь с профилем педагога;
* пользователь, имеющий оба профиля одновременно.

---

# 7. Подтверждение педагога

Регистрация педагога проходит в два этапа:

1. создание учетной записи;
2. подтверждение администрацией.

До подтверждения педагог не может использовать функции преподавателя.

Для этого используется поле:

```
is_approved
```

---

# 8. Правила доступа

Каждый объект может иметь один из двух уровней доступа.

### Публичный

Доступен всем пользователям сайта.

### Приватный

Доступен только:

* педагогу;
* ученику, которому принадлежит материал;
* администраторам.

---

# 9. Общая библиотека произведений

Все произведения хранятся в единой библиотеке.

Одно произведение может использоваться многими педагогами и многими учениками одновременно.

Произведения не дублируются.

---

# 10. Материалы произведения

Все дополнительные материалы выделяются в отдельную модель `MusicMaterial`.

Тип материала определяется полем `material_type`.

Возможные значения:

* ноты;
* минусовка;
* плюсовка;
* видео;
* текст произведения;
* другое.

Одно произведение может иметь неограниченное количество материалов.

---

# 11. История обучения

Связь между педагогом и учеником хранится в модели `TeachingAssignment`.

Она определяет:

* педагога;
* ученика;
* предмет;
* период обучения.

Все исполнения произведений относятся именно к этой связи.

---

# 12. Исполнение произведений

Каждое исполнение хранится в модели `Performance`.

Исполнение связано:

* с произведением;
* с конкретным процессом обучения (`TeachingAssignment`).

Дополнительно хранятся:

* оценка;
* комментарии;
* дата исполнения;
* видео исполнения;
* статус работы.

---

# 13. Оценивание

Используется единая пятибалльная шкала.

Допустимые значения:

```
0
1
2
3
4
5
```

---

# 14. Код проекта

Во всем проекте придерживаемся следующих принципов:

* понятные имена моделей;
* понятные имена полей;
* отсутствие дублирования данных;
* использование возможностей ORM вместо "ручного" SQL;
* повторное использование кода;
* соблюдение принципа DRY (Don't Repeat Yourself).

---

# 15. Документация проекта

В процессе разработки поддерживаются следующие документы:

* `PROJECT_SPECIFICATION.md` — описание проекта и архитектурные решения;
* `PROJECT_LOG` — журнал разработки;
* `RELATIONS.md` — связи между моделями;
* `IDEAS.md` — идеи для будущих версий;
* `PROJECT_STANDARDS.md` — настоящий документ.

Изменения архитектуры допускаются только до завершения этапа проектирования. После утверждения ER-диаграммы любые изменения должны быть обоснованы и задокументированы.
